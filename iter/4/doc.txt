5. Airflow DAG (rubric item 4)
      * Tasks: extract → load_staging → dbt_transform → verify → clone_dev_database
      * Error handling: retries=2, 1-min delay, on_failure_callback, transactional load with row-count check and rollback
      * Daily at midnight Pacific (catchup off): extract validates the CSV and PUTs it to the internal stage; load_staging runs DELETE, COPY (ON_ERROR='ABORT_STATEMENT'), and a row-count check in one transaction and rolls back on any error; Cosmos dbt_transform builds and tests the models; verify fails the run unless every product has exactly one current row (run 3: dim rows=2805, current=2551, products=2551, history=254); clone_dev_database is the daily 9.1 zero-copy dev clone.

     tags=["hw32"],
     default_args={"retries": 2, "retry_delay": timedelta(minutes=1),
                   "on_failure_callback": notify_failure})
def hw32_products_pipeline():
    ...
    @task
    def load_staging(expected: int) -> int:
        """Replace the RAW table in one transaction; roll back on any error or row-count mismatch."""
        with SnowflakeHook(snowflake_conn_id=SNOWFLAKE_CONN).get_conn() as conn:
            cur = conn.cursor()
            cur.execute("BEGIN")
            try:
                cur.execute(f"DELETE FROM {RAW_TABLE}")
                cur.execute(f"COPY INTO {RAW_TABLE} FROM @{STAGE} FILES=('{STAGED_FILE}') "
                            f"FILE_FORMAT=(FORMAT_NAME={FILE_FORMAT}) "
                            "FORCE=TRUE ON_ERROR='ABORT_STATEMENT'")
                loaded = cur.execute(f"SELECT COUNT(*) FROM {RAW_TABLE}").fetchone()[0]
                if loaded != expected:
                    raise ValueError(f"loaded {loaded} rows, expected {expected}")
            except Exception:
                cur.execute("ROLLBACK")
                raise
            cur.execute("COMMIT")
        logging.info("staging rows: %s", loaded)
        return loaded


    dbt_transform = dbt_group("dbt_transform")
    ...
    load_staging(extract()) >> dbt_transform >> verify() >> clone_dev_database

9.2 Point-in-time clone
         * hw32_eoy_snapshot runs at midnight on Jan 1, Pacific time (schedule 0 0 1 1 *). Its tasks: ◦ freeze_snapshot clones HW32.SNAPSHOTS.PRODUCTS_SNAPSHOT AT(TIMESTAMP => the year boundary) into PRODUCTS_SNAPSHOT_EOY_<year>, and points the view PRODUCTS_SNAPSHOT_FROZEN at that clone. 
         * The dbt model price_yoy compares each product's frozen price and title with today's dim_products, and labels it added, removed, repriced, retitled or unchanged. 
         * summarize_yoy logs the counts.
         * (evidence/src/dags__hw32_eoy_snapshot.py.txt, evidence/src/dbt_models__history__price_yoy.sql.txt)
         * Why one table and not the whole database: dbt rebuilds every ANALYTICS table with CREATE OR REPLACE on each run, which restarts its Time Travel history. The snapshot, by contrast, is merged in place. It is a TRANSIENT table (dbt's default), so Time Travel reaches back only 1 day (the log shows retention=1). That is why the clone must be taken at the year boundary: a year-end state cannot be cloned weeks later.

9.4 Backup and restore
         * Daily backup: hw32_daily_backup runs at midnight Pacific. Its tasks: 
         * backup_name derives HW32_BACKUP_<yyyymmdd> from the run's Pacific date. Airflow 3 manual runs have no logical date, so the spec's {{ ds_nodash }} is undefined there. 
         * backup_database runs CREATE DATABASE IF NOT EXISTS HW32_BACKUP_<yyyymmdd> CLONE HW32. IF NOT EXISTS means a second run on the same day cannot overwrite a good backup. 
         * prune_old_backups drops every backup dated before today minus 6 days, so it keeps 7: today's and the 6 before it.

10. Takeaways and Cost (rubric item 10)
         1. The snapshot strategy has to fit the data. The assignment's example snapshot uses the timestamp strategy on an updated_at column (evidence/00_assignment_snapshot_excerpt.txt), and this dataset has none. Its only time column, scraped_at, holds the scrape time: every row's value falls between 00:55 and 01:05 on Dec 14, 2021 (evidence/02_dataset.txt). mutate_source.py never changes it: scraped_at changed in 0 rows in both runs (evidence/08_source_diffs.txt). A timestamp snapshot on scraped_at would therefore have recorded none of the changes. The check strategy on title, price, availability and brand recorded every one of them: 2,551 + 127 + 127 = 2,805 snapshot rows (evidence/08_snapshot_by_run.txt). One of the four columns, availability, is "InStock" in all 2,551 rows, so in this data it never triggered a version. The strategy has to come from what the source can actually show, not from the template.
         2. Zero-copy clones are copy-on-write, so a clone costs no storage of its own until it changes. Every day HW32 is cloned twice, once to the dev database and once to a dated backup, and the restore swapped in a cloned schema. TABLE_STORAGE_METRICS for PRODUCTS_SNAPSHOT shows the backup and the dev clone owning 0 active bytes. Prod owns 1,153,024 active bytes, plus 1,099,264 bytes kept for Time Travel. The schema left behind by the restore still holds 1,104,896 bytes (evidence/10_storage_metrics.txt). A clone starts costing storage only once one side changes, and leftovers such as the pre-restore schema keep costing until they are dropped.
         3. Time Travel is short for dbt's tables, so point-in-time work has to be scheduled. dbt creates its tables and snapshots on Snowflake as TRANSIENT: the year-end DAG logs "kind=TRANSIENT retention=1 day(s)", and SHOW TABLES gives retention_time 1 for the snapshot and the ANALYTICS tables (evidence/92_eoy_logs.txt, evidence/92_price_yoy.txt). A Time Travel query back to 1:15 AM on Nov 24 still worked that evening, returning 2678 rows then against 2805 now (evidence/10_timetravel_before_run3.txt). Anything older than a day is out of reach. That is why 9.2 clones at the year boundary instead of reconstructing the year end later.
         4. Retries fix temporary faults, not configuration errors. The DAGs' default arguments set retries=2 with a 1-minute delay, and the pipeline has a failure callback. On Nov 23, extract failed three times, a minute apart, with "The conn_id snowflake_conn isn't defined". At midnight on Nov 24, extract and backup_database each failed three times with "Cannot specify basic authenticator together with private key parameters". Both times the pipeline's callback logged "HW32 pipeline FAILED at task extract (try 3)" (evidence/04_retry_callback_extract.txt, evidence/01_snowflake_jwt_failure.txt). The retries only delayed each failure by about two minutes. The fix both times was configuration: defining the connection, then adding authenticator SNOWFLAKE_JWT. After that fix, the Nov 24 tasks succeeded on try 4. The callback logged which task failed and on which try.
         5. Cost comes from idle warehouse time, not from query time. Two X-Small warehouses were used: HW32_WH for the pipeline (auto-suspend 60 s) and COMPUTE_WH, Snowsight's default (auto-suspend 300 s). From WAREHOUSE_METERING_HISTORY and QUERY_HISTORY since Nov 19 (evidence/10_credits_r3.txt):

warehouse    credits  queries  execution minutes  auto-suspend
COMPUTE_WH    1.262    1670          1.5             300 s
HW32_WH       0.889     742          2.5              60 s
COMPUTE_WH cost more with less execution time. Snowflake bills a running warehouse per second, with a 60-second minimum each time it resumes, until auto-suspend stops it (Snowflake documentation). So most of the bill is idle time after queries finish. HW32_WH's 60 s auto-suspend gives it a lower bill per execution minute, but idle time dominates its bill too. The metering view can lag by up to about 3 hours (Snowflake documentation), so these totals may not include the latest runs. HW32_WH's total rose from 0.791 to 0.889 credits between captures an hour apart (evidence/10_credits.txt, evidence/10_credits_r3.txt).
